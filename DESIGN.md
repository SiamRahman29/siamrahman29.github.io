## Approaches Considered

### Approach A: One-pager
Single scrollable page; everything on /. About 1.5 days. Fastest. Rejected because no shareable per-project URLs is a significant cost for a job-hunt portfolio.

### Approach B: Full multi-page (CHOSEN)
Homepage scannable; each featured project and writing post gets its own page. About 3 days. Most extensible.

### Approach C: Hybrid
One-page home + dedicated detail pages for case studies + /writing pages. About 2.5 days. Sweet spot, but user picked B for max extensibility.

## Recommended Approach: B, Full Multi-Page

## Engineering Specifications (added by /plan-eng-review on 2026-05-20)

### Hosting mode

- **GitHub Pages user-site mode.** Rename repo from `dev-portfolio` to `siamrahman29.github.io`. Site lives at `https://siamrahman29.github.io`.
- **Astro config:** `base: '/'`, `site: 'https://siamrahman29.github.io'`. When custom domain ships, only `site` changes; `base` stays.
- **CNAME file:** add `/public/CNAME` containing the custom domain when ready. GitHub Pages reads it on every deploy.

### Version pinning

- **Astro v5** (current as of 2026-05). Uses the new `defineCollection({ loader, schema })` content collections API.
- **Tailwind v4** with `@tailwindcss/vite` plugin, not the v3 PostCSS setup.
- **Node 22 LTS** in CI.

### Content collection schemas

`src/content.config.ts` defines two collections:

```ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const projects = defineCollection({
  loader: glob({ pattern: '**/*.md', base: './src/content/projects' }),
  schema: z.object({
    title: z.string(),
    slug: z.string(),
    summary: z.string(),
    role: z.string(),
    tech: z.array(z.string()),
    period: z.string(),
    links: z.array(z.object({ label: z.string(), href: z.string().url() })).optional(),
    featured: z.boolean().default(false),
    order: z.number().default(99),
    ogImage: z.string().optional(),
  }),
});

const writing = defineCollection({
  loader: glob({ pattern: '**/*.md', base: './src/content/writing' }),
  schema: z.object({
    title: z.string(),
    summary: z.string(),
    date: z.coerce.date(),
    draft: z.boolean().default(false),
    ogImage: z.string().optional(),
    tags: z.array(z.string()).default([]),
  }),
});

export const collections = { projects, writing };
```

Featured projects on the homepage filter on `featured: true` and sort by `order`.

### OG image strategy

- **Per-page hand-authored OG images.** 1200x630 PNG. Filename matches slug.
- Stored in `/public/og/[slug].png`.
- Each page's frontmatter `ogImage` field references it.
- Fallback default: `/public/og/default.png` (one designed card with name + headline) for any page missing a custom OG.
- Maintenance commitment: every new post / project requires a designed OG before publish.

### CI / GitHub Actions workflow

`.github/workflows/deploy.yml` uses the official Astro action plus quality gates:

```
1. checkout
2. setup-node@v4 with Node 22
3. npm ci
4. astro check (typecheck + integrity)
5. astro build
6. lychee (link checker) on /dist  → fails on broken internal links
7. Lighthouse CI on /, /about, /writing, one project page  → fails if <95 on any metric
8. withastro/action@v3 → upload artifact + deploy to Pages
```

All free. Total CI time target: under 3 minutes per push.

### Image strategy

- Source images in `src/assets/` for Astro `<Image>` optimization (auto WebP, responsive srcset).
- Public assets (resume PDF, favicon, OG images) in `/public/`.
- All `<Image>` calls include explicit `width` and `height` to prevent CLS.
- Profile photo: single source, 800x800, Astro generates responsive variants.

### Font strategy

- Self-hosted via `@fontsource-variable/inter` and `@fontsource-variable/jetbrains-mono`.
- Subset to Latin only.
- `font-display: swap`.
- No Google Fonts CDN (avoids render-blocking + privacy headers issue).

### JS budget

- 0 KB JS by default. Astro ships zero unless an island declares `client:*`.
- All animations are pure CSS (`@keyframes`, `transition`, view transitions API).
- Only client-side JS allowed in v1: email obfuscation (~200 bytes) and Astro's built-in prefetch.

### 404 page

`src/pages/404.astro` renders a styled 404 with a link back to home. GitHub Pages serves this for any unmatched route.

### Failure modes (catalogued)

| Failure | Likely? | Detected by | User-visible? |
|---|---|---|---|
| GitHub Pages serves at `/dev-portfolio/` because repo not renamed | High if forgotten | First deploy | Yes — broken nav |
| Lighthouse drops below 95 from unoptimized image | High over time | Lighthouse CI | No (CI fails before deploy) |
| External link in writing post 404s | Medium over time | lychee in CI | CI fails before deploy |
| Custom OG missing for new post | High (human forgets) | Manual review | Yes — ugly Slack unfurl |
| Cal.com booking link expires / account paused | Low | None | Yes — silent fail |
| Resume PDF goes stale | Certain | None | Yes — recruiter sees old experience |

The Cal.com link and stale resume are the two silent-failure risks. Mitigation: add a calendar reminder ("review portfolio once a month: update resume, verify Cal.com link works, refresh writing").

### Worktree parallelization

Sequential implementation, no parallelization opportunity. This is a single-developer 22-25 hour build with strong file-order dependencies (scaffold → layout → home → detail pages → polish). Splitting across worktrees would create more coordination overhead than time saved.
